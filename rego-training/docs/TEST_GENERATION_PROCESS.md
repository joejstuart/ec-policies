# Test Generation Process

This document explains how tests were created for each Rego rule.

## Overview

Tests for Rego rules were generated **automatically** using a pattern-matching script, not by an AI model. The process involved:

1. **Pattern-based test generation** - A Python script (`generate_validation_tests.py`) analyzes natural language descriptions and automatically generates test data
2. **Rule-based heuristics** - The script uses pattern matching on keywords, field names, and natural language to determine what tests to create
3. **No AI/LLM involved** - The test generation is purely algorithmic, based on predefined patterns

## The Process

### Step 1: Comprehensive Test Cases

The initial test cases were created in `data/comprehensive_test_cases.json`. This file contains:
- Natural language descriptions
- Rego code (likely generated by an AI model initially)
- Keys used in the rule
- Test case type

**Note**: The Rego code in `comprehensive_test_cases.json` may have been generated by an AI model, but the **test data itself** was generated automatically.

### Step 2: Automatic Test Generation

The script `scripts/core/generate_validation_tests.py` automatically generates test data by:

1. **Reading** `data/comprehensive_test_cases.json`
2. **Analyzing** each test case's:
   - Natural language description
   - `keys_used` field (which JSON paths the rule checks)
   - Test case type
3. **Pattern matching** against ~100+ predefined patterns to determine:
   - What the rule is checking (status, parameters, annotations, etc.)
   - What positive test data should look like (violates the rule)
   - What negative test data should look like (satisfies the rule)
4. **Generating** test data structures with:
   - Positive tests (`should_deny: true`) - when condition is violated
   - Negative tests (`should_deny: false`) - when condition is met

### Step 3: Output

The script outputs `data/test_case_definitions.json` with:
- Each test case ID
- Natural language description
- Generated test data (positive and negative cases)
- Expected deny messages

## How Pattern Matching Works

The script uses pattern matching on natural language and `keys_used` to identify what to test. Examples:

### Pattern: Task Status Check

**Natural Language**: "Verify all tasks have status 'Succeeded'."

**Pattern Detection**:
- `"status"` in natural language
- `"task.status"` in `keys_used`
- `"all tasks"` in natural language

**Generated Tests**:
- **Positive**: Task with `status: "Failed"` → should deny
- **Negative**: All tasks with `status: "Succeeded"` → should pass

### Pattern: Parameter Value Check

**Natural Language**: "Verify the build task has parameter 'mode' set to 'strict'."

**Pattern Detection**:
- `"parameter"` in natural language
- `"task.invocation.parameters"` in `keys_used`
- Task name specified ("build")
- Parameter name and value specified

**Generated Tests**:
- **Positive**: Build task with `parameters.mode: "permissive"` → should deny
- **Negative**: Build task with `parameters.mode: "strict"` → should pass

### Pattern: Annotation Check

**Natural Language**: "Verify the build task has annotation 'tekton.dev/tags' set to 'konflux'."

**Pattern Detection**:
- `"annotation"` in natural language
- `"task.invocation.environment.annotations"` in `keys_used`
- Annotation key and value specified

**Generated Tests**:
- **Positive**: Build task with wrong annotation value → should deny
- **Negative**: Build task with correct annotation value → should pass

## Pattern Examples in Code

The script contains ~100+ patterns like:

```python
# Pattern: Check task status
if "status" in nl_lower and "task.status" in str(keys_used):
    # Positive test: task with wrong status
    task["status"] = "Failed"
    tests.append({"should_deny": True, ...})
    
    # Negative test: task with correct status
    task["status"] = "Succeeded"
    tests.append({"should_deny": False, ...})

# Pattern: Check parameter value
if "parameter" in nl_lower and "task.invocation.parameters" in str(keys_used):
    # Extract parameter name and value from natural language
    # Generate positive/negative tests
    ...
```

## Why Pattern-Based?

1. **Consistency**: All tests follow the same structure
2. **Coverage**: Ensures both positive and negative cases are generated
3. **Speed**: Much faster than manual test creation
4. **Maintainability**: Patterns can be updated to handle new cases

## Limitations

The pattern-based approach has limitations:

1. **Complex rules**: May not handle very complex logic perfectly
2. **Edge cases**: Some edge cases might need manual adjustment
3. **Pattern coverage**: New rule types may need new patterns added

- **`data/test_case_definitions.json`** - Generated test data (42,369 lines)

## Adding New Patterns

To add support for new test types:

1. Identify the pattern in natural language and `keys_used`
2. Add a new pattern check in `generate_validation_tests.py`
3. Generate positive and negative test data
4. Test the pattern with sample cases
5. Regenerate `test_case_definitions.json`

## Summary

**Tests were NOT generated by an AI model** - they were generated automatically using pattern matching. The script analyzes natural language descriptions and JSON paths to determine what tests to create, then generates appropriate test data structures.

The only part that may have involved an AI model was the initial creation of Rego code in `comprehensive_test_cases.json`, but the test data generation itself is purely algorithmic.
